# Audit runtime GPTina Offline — 23 settembre 2026

## Perimetro

Audit del percorso locale:

`launcher → llama.cpp → memory runtime → RAG/chat bridge → browser`

Repository verificata: `MATRIXNEO23/scodinzolina-offline`.

La repository canonica `MATRIXNEO23/scodinzolina-conntinuity` non viene modificata.

## Problemi trovati

### 1. Chat non streaming

**Impatto:** alto.

Il bridge chiamava `/v1/chat/completions` con `stream: false`. Su una CPU lenta la pagina restava apparentemente ferma fino alla fine della generazione.

**Fix:** endpoint `/chat/stream` nel bridge, proxy dello stream SSE di llama.cpp e rendering token-per-token nella UI.

### 2. Timeout generazione troppo corto

**Impatto:** alto sul PC target.

La richiesta sincrona aveva timeout di 300 secondi. Su un i3-2100 una risposta lunga può superarlo.

**Fix:** timeout configurabile, default 900 secondi. Lo streaming rende inoltre visibile l'avanzamento.

### 3. Nessuna diagnostica live

**Impatto:** alto.

I processi venivano nascosti con `CREATE_NO_WINDOW`; gli errori finivano nei file log ma non erano facilmente visibili.

**Fix:** finestra grafica **Diagnostica / errori** con:
- stato motore/memoria/chat;
- `engine.log`;
- `memory.log`;
- `chat.log`;
- log del launcher;
- refresh automatico.

Gli errori di avvio aprono automaticamente la diagnostica sul componente pertinente.

### 4. Chiamate Tkinter da thread secondari

**Impatto:** medio-alto.

Il launcher aggiornava widget e message box direttamente dai worker thread. Tkinter non garantisce sicurezza in questo uso e può bloccarsi o comportarsi in modo intermittente.

**Fix:** coda thread-safe; solo il thread UI modifica widget e finestre.

### 5. Context non controllato realmente

**Impatto:** alto.

Il bridge limitava singole stringhe, ma non verificava che:

`system + memoria + history + messaggio + risposta`

entrassero nel context effettivo del motore.

**Fix:** il bridge legge `n_ctx` da `/props`, usa `/apply-template` + `/tokenize` per contare il prompt e riduce in ordine:
1. history più vecchia;
2. frammenti memoria meno prioritari;
3. lunghezza dei frammenti;
4. summary live.

Il turno utente corrente viene preservato; se non entra, viene restituito un errore esplicito.

### 6. Max risposta del launcher non propagato al bridge

**Impatto:** medio-alto.

Il campo **Max risposta** configurava il server, mentre il bridge continuava a usare il valore tracciato in `chat_config.json`.

**Fix:** il launcher scrive un file locale ignorato da Git:

`offline-runtime/.gptina_runtime_config.json`

Il bridge lo sovrappone alla configurazione base.

### 7. Retrieval memoria ripetitivo

**Impatto:** medio sul vecchio hardware.

Per una singola domanda il bridge poteva provocare più scansioni complete della repository: frase intera + termini estratti.

**Fix:** nuovo endpoint read-only `/search_multi`: tutte le query vengono valutate in una sola scansione e i risultati sono ordinati per numero/specificità dei match.

### 8. Servizi vecchi o porte occupate accettati troppo facilmente

**Impatto:** alto durante aggiornamenti/test.

Il launcher controllava principalmente che una porta rispondesse; una vecchia istanza del bridge o KoboldCpp poteva essere riutilizzata involontariamente.

**Fix:**
- versionamento API del memory runtime e chat bridge;
- verifica nome servizio + versione;
- il motore deve rispondere a `/props` come llama.cpp;
- se la porta contiene un servizio vecchio/inatteso, il launcher si ferma con errore chiaro.

### 9. Modello già attivo diverso da quello selezionato

**Impatto:** medio.

Un llama-server già in ascolto poteva essere riutilizzato anche con un altro GGUF.

**Fix:** confronto del nome modello esposto da `/props` con il GGUF selezionato.

### 10. Thinking di Qwen può consumare token/tempo

**Impatto:** medio-alto sui Qwen che supportano thinking.

**Fix:** le richieste inviano:
- `chat_template_kwargs.enable_thinking=false`;
- `reasoning_effort=none`.

Se il template ignora la richiesta e produce solo reasoning, il bridge restituisce un errore diagnostico invece di lasciare la chat vuota.

### 11. Nessuna telemetria visibile

**Impatto:** medio.

Era difficile distinguere lentezza di retrieval, prompt processing e generazione.

**Fix:** la chat mostra, quando disponibili:
- token prompt / context;
- tempo retrieval memoria;
- tempo preparazione;
- tempo al primo token;
- token/sec della generazione;
- prompt token/sec.

Il bridge espone anche `/diagnostics` e interroga `/slots` di llama.cpp.

### 12. Log cumulativi tra avvii

**Impatto:** basso-medio.

I log erano aperti in append, quindi un errore corrente poteva confondersi con sessioni precedenti.

**Fix:** a ogni avvio il log corrente viene ruotato in `.previous` e la nuova sessione parte pulita.

## Verifiche mantenute

- memory runtime ancora read-only;
- binding solo su `127.0.0.1`;
- nessuna funzione Git nel runtime;
- nessuna scrittura automatica nella continuity;
- build del motore Sandy Bridge separata dalla memoria;
- motore costruito con SSE4.2 + AVX e AVX2/FMA/F16C disabilitati;
- compatibilità KoboldCpp resta soltanto nel bridge come fallback diagnostico, non nel percorso normale.

## Limite dell'audit remoto

La CI può verificare sintassi, test, build del motore e packaging, ma non può emulare fedelmente l'i3-2100 reale.

Dopo la pubblicazione il test decisivo sul PC target resta:

1. avvio con il GGUF scelto;
2. verifica `motore OK / memoria OK / chat OK`;
3. una risposta breve;
4. lettura dei token/sec mostrati dalla chat;
5. confronto 2 thread vs 4 thread sullo stesso prompt.

Solo il test sul PC reale può stabilire la configurazione CPU più veloce.
