# Audit PC i3-2100 ↔ GPTina Offline

**Data:** 24 settembre 2026. **Base:** `main` `05bdfc0ff82bc196a7af2d1b7ec57f2e34c7fe50` e log reali condivisi da Alberto. L'audit riguarda la macchina osservata e il motore distribuito; le prestazioni dell'app 2.0/2.1 con il nuovo indice generale non sono ancora misurate sul PC.

## 2. Percorso e colli di bottiglia

`launcher Python → llama-server compilato → memory server Python → bridge/chat → browser`.

- Il launcher prima di questa modifica esponeva modello, `-t`, context e Max risposta; fissava `-tb` allo stesso valore di `-t`, `-b 256`, `-ub 128`, un solo slot, CPU only e Flash Attention off.
- Il benchmark sul PC con **lo stesso prompt di 282 token e lo stesso 4B** misura `-tb 2/3/4`: primo token cold **86,3 / 72,4 / 66,4 s**, prompt **3,27 / 3,90 / 4,25 tok/s**, CPU **1,93 / 2,57 / 3,21 core equivalenti**. `-tb 4` risparmia 19,9 s sul cold, ma usa molto più tempo CPU. Una replica per configurazione; non è una misura della chat variabile.
- Nella chat tecnica il prompt da 232 token ha richiesto 63,7 s al primo token; con 285 token in cache il secondo turno è sceso a 14,1 s. Quando il prefisso si interrompe, la latenza risale. La stabilità del prompt è quindi un fattore misurato, non solo un'ipotesi.
- In una domanda personale il prompt da 768 token ha ricalcolato 763 token e atteso 278,9 s; ricerca memoria circa 0,5 s. In una schermata successiva la ricerca era circa 0,6 s e il prefill circa 208 s per 439 token nuovi. Il carico dominante in queste prove è l'elaborazione del prompt da parte del 4B, non il tempo della ricerca Python.
- Il nuovo indice FTS5 in memoria riduce la ricerca di candidati e filtra versioni invalidate/superate. È lessicale e il bridge passa soltanto pochi frammenti; i test locali di recall non provano fedeltà della risposta o latenza sull'i3.

## 3. Valutazione per componente

| Componente | Stato | Rischio residuo / azione |
| --- | --- | --- |
| Build CPU | ISA adatta all'i3-2100 e revisione fissata. | Verificare `--version` del binario installato e hash dello ZIP quando si aggiorna il motore; non cambiare ISA per provare un modello. |
| Thread generazione `-t` | Default 2 coerente con 2 core fisici. | Nessuna prova controllata che 3/4 migliorino decode; compararli separatamente da `-tb`. |
| Thread prompt `-tb` | Default 2 prudente; prova reale 4 più rapida nel cold. | 4 porta il carico a 3,21 core equivalenti. Parametro configurabile; prova in chat con carico di fondo simile. |
| Batch/micro-batch | 256/128 attuali, già presenti nella matrice benchmark completa. | Non c'è un vincitore affidabile per la chat reale. Esporre valori validati, non imporre un nuovo default senza prova. |
| Context/output | 1024/160 attuali; il context fitter sacrifica history se il prompt cresce. | Aumentare context può conservare history ma non riduce i token da elaborare. Un output di 160 token tronca alcune risposte. |
| Memoria/RAG | Nuovo indice locale FTS5, due frammenti personali brevi. | Misurare recall di domande parafrasate, status/provenance e fedeltà: una fonte lessicalmente vicina non prova ogni frase generata. |
| Cache | `cache_prompt` attiva, un solo slot. | Tracciare `cache_n`, `prompt_n` e hash del system nelle chat reali dopo ogni modifica del prompt. |
| Modelli alternativi | Nessuna misura i3 per 0.6/0.8/1.7B abliterated. | Smoke test del template/runtime e benchmark comparativo. Qwen3.5 richiede verifica di compatibilità con il motore fissato. |

## 4. Modifica minima proposta e implementata

Il launcher 2.1 conserva i default e rende configurabili `-tb`, `-b`, `-ub`, oltre a modello, `-t`, context e Max risposta. Valida intervalli e `ubatch ≤ batch`, salva il profilo locale e mostra i valori applicati nel log. Rifiuta il riuso di un motore già attivo i cui thread/batch non sono verificabili da `/props`; serve fermare e riavviare per cambiare profilo. Non modifica build, memoria canonica o quantizzazione.

**Prova A/B raccomandata:** stesso Qwen3 4B, stessa domanda e carico di fondo; `-t 2`, `-b 256`, `-ub 128`, context 1024, Max 160; cambiare soltanto Thread prompt 2→4. Ripetere cold almeno due volte e una chat di tre turni; confrontare `prompt_n`, `cache_n`, primo token, tok/s e risposta. Poi usare un piccolo modello come esperimento separato, senza attribuire al runtime guadagni che derivano dalla dimensione del modello.

## 5. Dati mancanti per chiudere l'audit hardware

GPU/driver reali; frequenza e throttling durante 3–5 minuti di prefill; RAM libera e page faults durante la chat; canali/frequenza RAM; revisione/hash dell'EXE effettivamente installato; misura 2.1 sul PC. Nessuno di questi va dedotto dal solo nome della CPU o dalla CI Windows.
